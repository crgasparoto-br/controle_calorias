## Objetivo

Garantir que comandos do WhatsApp que informem uma data explícita ou relativa — por exemplo `hoje`, `ontem`, `anteontem` ou `amanhã` — adicionem alimentos somente à refeição correspondente ao dia solicitado, sem reutilizar silenciosamente uma refeição homônima de outro dia.

> Branch base para implementação: `develop`.
>
> `specification_version: 2`

## Contexto

Foi reproduzido o seguinte comportamento em produção:

> `adiciona ao café da manhã de hoje, 60g pão francês, 1 fatia de presunto, 1 fatia de mussarela, 60g requeijão catupiry light, 1 ovo frito, 3 xícaras de café sem açúcar`

O sistema respondeu que os alimentos foram adicionados ao **Café da manhã de 22/08/2026**, embora a mensagem tenha sido enviada em **24/08/2026** e tenha solicitado explicitamente **"de hoje"**.

Na `develop`, o parser resolve corretamente `hoje` a partir de `receivedAt`. O problema está na seleção da refeição existente: o helper de busca tenta primeiro nome + dia e, se não encontra, faz fallback para `matches[0]`, podendo retornar uma refeição com o mesmo nome de outra data. O fluxo então chama `updateMeal()` usando essa refeição antiga.

A fonte canônica de comportamento já existente é `docs/design-docs/whatsapp-ingestion.md`: pedidos de adição a uma refeição indicada devem atualizar a refeição do dia interpretado e, quando essa refeição não existir naquele dia, o sistema deve **pedir esclarecimento antes de alterar qualquer registro**. Portanto, criar automaticamente uma nova refeição nesse cenário também viola o contrato atual.

Há um fluxo estruturado mais recente que já diferencia data explícita de data implícita e só permite fallback entre dias quando a data não foi explicitada. Esta issue deve alinhar os fluxos de adição alimentar a essa regra sem introduzir uma segunda regra temporal concorrente.

## Escopo

- Corrigir a seleção da refeição-alvo em comandos de adição de alimentos via WhatsApp.
- Considerar como data explícita, no mínimo: `hoje`, `ontem`, `anteontem` e `amanhã`.
- Impedir fallback para refeição de outro dia quando a data foi explicitada pelo usuário.
- Quando a refeição indicada não existir no dia interpretado, pedir esclarecimento sem criar nem alterar registro alimentar.
- Preservar o comportamento contextual atual quando a mensagem não trouxer data explícita, desde que continue compatível com as regras canônicas do produto.
- Garantir paridade do contrato entre os entrypoints de WhatsApp que possam executar adição de alimentos.

## Fora de escopo

- Alterar cálculos nutricionais dos alimentos.
- Alterar reconhecimento de quantidades, marcas ou unidades, exceto se necessário para manter o mesmo comando de regressão funcional.
- Reestruturar todo o pipeline de intents do WhatsApp.
- Alterar regras de criação de refeição para outros tipos de registro que não sejam o comando de adicionar alimento a uma refeição indicada.

## Requisitos funcionais

1. Quando a mensagem contiver uma data explícita/relativa, a busca da refeição deve ficar restrita ao dia resolvido no timezone do usuário.
2. Se existir uma refeição com o mesmo rótulo no dia solicitado, os novos itens devem ser adicionados somente a ela.
3. Se não existir uma refeição compatível no dia solicitado, o sistema não pode atualizar uma refeição homônima de outro dia.
4. Se a refeição indicada não existir no dia interpretado, o sistema deve retornar esclarecimento e **não pode chamar persistência para criar uma nova refeição nem alterar refeição existente de outro dia**.
5. A resposta ao usuário deve refletir a data efetivamente utilizada na persistência quando houver mutação; no caso de esclarecimento por refeição ausente, não deve afirmar que algo foi registrado.
6. O timezone utilizado para interpretar `hoje`/`ontem` deve ser o timezone do usuário já resolvido pelo pipeline; o fallback padrão continua sendo o configurado pelo projeto quando não houver timezone do perfil.
7. O contrato deve ser coerente tanto no simulador/serviço quanto no webhook real: data explícita nunca permite fallback cross-day nem criação automática de refeição ausente para este comando.
8. A implementação deve preservar a distinção entre **data resolvida** e **data explicitamente informada**. A mera presença de `parsed.date` não prova explicitude, pois o parser também usa `recentDate`/`referenceDate` quando o usuário não informa data.

## Cenários e casos de borda

### Data explícita com refeição existente

Dado que existe `Café da manhã` em 24/08/2026 e também em 22/08/2026, ao receber:

`adiciona ao café da manhã de hoje, 60g pão francês`

somente a refeição de 24/08/2026 deve ser alterada.

### Data explícita sem refeição no dia

Dado que existe `Café da manhã` em 22/08/2026, mas não em 24/08/2026, ao receber:

`adiciona ao café da manhã de hoje, 60g pão francês`

nenhuma refeição de 22/08/2026 pode ser alterada, nenhuma nova refeição deve ser criada e o usuário deve receber esclarecimento informando que a refeição indicada não foi encontrada no dia interpretado.

### Outras referências relativas

Aplicar a mesma regra para:

- `ontem`
- `anteontem`
- `amanhã`

### Sem data explícita

Comandos sem referência temporal explícita devem continuar seguindo o comportamento contextual atual. Não é permitido desabilitar esse comportamento apenas porque o parser retornou uma `date` preenchida por `referenceDate` ou `recentDate`.

### Virada de dia/timezone

A comparação de dia deve usar o timezone resolvido do usuário e não UTC puro, especialmente em mensagens próximas à meia-noite.

## Invariantes estruturais

### `must_not_behave`

- Com data explícita, nunca atualizar uma refeição homônima de outro dia nem criar automaticamente uma nova refeição quando a refeição indicada estiver ausente no dia interpretado.
  - **Implementação errada plausível:** remover o fallback cross-day, mas deixar `executeWhatsappDatedFoodAdditionIntent` cair em `createManualMeal()` quando não encontrar a refeição; o caso feliz com refeição existente passa, mas o contrato canônico continua violado.
  - **Controle discriminante:** regressão com data explícita + refeição ausente verifica resposta de esclarecimento e ausência de chamadas a `updateMeal()` e `createManualMeal()`.

### `precedence_invariants`

- A informação de que a data foi explicitamente informada pelo usuário deve sobreviver até a seleção da refeição; a data resolvida por fallback contextual não pode ser reinterpretada como explícita.
  - **Implementação errada plausível:** tratar qualquer `parsed.date` não nula como data explícita, desabilitando fallback contextual também em comandos sem `hoje`/`ontem`/`anteontem`/`amanhã`.
  - **Controle discriminante:** testes pareados para o mesmo comando com e sem referência temporal provam que somente o primeiro bloqueia fallback cross-day.

### `forbidden_implementation`

- É proibido corrigir apenas o caminho feliz removendo globalmente `matches[0]` sem preservar explicitamente os consumidores que ainda dependem do comportamento contextual sem data explícita.
  - **Implementação errada plausível:** alterar o helper compartilhado para nunca fazer fallback entre dias; os testes desta reprodução passam, mas comandos contextuais existentes sem data explícita deixam de funcionar.
  - **Controle discriminante:** cobertura dos consumidores do helper e regressão específica para comando sem data explícita, além dos casos com data explícita.

## Critérios de aceite

- [ ] O comando da reprodução enviado em 24/08/2026 com `café da manhã de hoje` nunca atualiza uma refeição de 22/08/2026.
- [ ] Com data explícita, nenhuma função de seleção retorna refeição de outro dia como fallback silencioso.
- [ ] Quando há refeição compatível no dia solicitado, somente essa refeição é atualizada.
- [ ] Quando não há refeição compatível no dia solicitado, o resultado é esclarecimento e nenhuma refeição é criada ou alterada.
- [ ] O fluxo de data explícita ausente não chama `createManualMeal()` como fallback para este comando.
- [ ] A resposta do WhatsApp informa a mesma data que foi efetivamente persistida; esclarecimentos não afirmam registro inexistente.
- [ ] `hoje`, `ontem`, `anteontem` e `amanhã` possuem cobertura automatizada.
- [ ] Há cobertura de regressão para timezone, incluindo pelo menos um caso próximo à mudança de dia.
- [ ] Há regressão para comando equivalente sem data explícita, provando que a correção não transforma toda `parsed.date` em data explícita.
- [ ] Os entrypoints `simulateWhatsappInbound` e webhook real obedecem ao mesmo invariante de não mutação cross-day e não criação automática quando a refeição indicada estiver ausente.
- [ ] Testes existentes de adição alimentar e datas explícitas continuam passando.

## Impacto na documentação

- `docs/design-docs/whatsapp-ingestion.md` já contém o contrato canônico necessário e não precisa mudar para esta correção, salvo se a implementação revelar inconsistência documental adicional.
- A implementação deve restaurar conformidade do código com essa fonte, não criar uma regra paralela em comentário, PR ou teste isolado.

## Riscos e dependências

- Existem múltiplos caminhos de interpretação/execução para adição alimentar no WhatsApp. A correção não deve ficar restrita a um único handler se outro entrypoint ainda puder fazer fallback cross-day ou criar refeição ausente contrariando o contrato canônico.
- `server/modules/whatsapp/intent/mealItemHelpers.ts` atualmente faz fallback para `matches[0]` após falhar a busca no dia.
- `server/modules/whatsapp/datedFoodAdditionIntent.ts` atualmente cria uma nova refeição quando não encontra a refeição alvo; esse comportamento conflita com `docs/design-docs/whatsapp-ingestion.md` para o comando desta issue e deve ser corrigido.
- `parseMealCommandFromWhatsApp` sempre pode produzir uma data a partir de `recentDate`/`referenceDate` mesmo sem expressão temporal explícita; portanto a decisão de permitir fallback cross-day não pode depender apenas de `parsed.date !== null`.
- O fluxo estruturado em `server/modules/whatsapp/structuredCoffeeIntentActions.ts` já modela separadamente `date` e `explicit` e só habilita fallback cross-day quando `explicit === false`; essa semântica deve ser preservada, sem obrigar duplicação literal da implementação.
